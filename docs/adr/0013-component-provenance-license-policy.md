# ADR-0013: 组件来源与许可策略

日期：2026-10-23｜状态：Accepted

## 背景

后续可能把 JBIG2、JPX、ICC、CFF/Type1、CMS、光栅和写入组件改为自研或内部化，
并从成熟实现中提炼核心算法。不同来源的许可差异很大：OpenJPEG、lcms2、FreeType
可提供宽松许可参考，Poppler 是 GPL，MuPDF 是 AGPL。若没有来源和许可门禁，代码
进入仓库后很难补救，也会影响 Apache-2.0 发布和下游集成。

本 ADR 约束所有新增代码、生成代码、测试向量和参考实现，不只约束 Go module。

## 决策

### 1. 每个组件先分类，再写代码

每个组件必须属于以下一种来源类别：

| 类别 | 定义 | 处理 |
| --- | --- | --- |
| **Original** | 完全由本项目按规范实现 | 正常版权与测试 |
| **Permissive fork** | 从 MIT/BSD/Apache/ISC/Zlib/FTL 等内部化 | 保留版权、许可、NOTICE、commit 和修改记录 |
| **Clean-room** | 参考规范/行为，不复制受限代码 | 记录输入材料和隔离过程 |
| **External reference** | 只用于黑盒差分、性能或行为对照 | 不把代码或测试代码复制进仓库 |
| **External runtime** | 通过进程/服务调用 | 单独部署、单独许可、能力报告 |

禁止“来源不明”“网上片段”“凭记忆重写”的组件进入核心。

### 2. 许可分级

| 级别 | 许可 | 核心策略 |
| --- | --- | --- |
| **Green** | MIT、BSD-2/3、Apache-2.0、ISC、Zlib、FTL、公共领域 | 可内部化；保留声明并登记 |
| **Yellow** | LGPL、MPL、EPL 等弱 copyleft | 仅独立模块/动态链接/独立进程；逐文件法务确认 |
| **Red** | GPL、AGPL、未知或不兼容许可 | 不复制、不链接、不进入测试代码；只能黑盒参考或外部进程 |

补充规则：

- 许可按**文件**核对，不按项目首页判断；一个项目可能混合多种许可。
- 字体程序、ICC profile、CMap 数据、测试 PDF 是独立内容许可，不能只看代码许可。
- 生成的查找表/常量如来自受限实现，也视为衍生内容。
- 许可不明确时默认 Red，直到法务书面确认。
- 自研不自动免除标准必要专利风险；JPEG2000、JBIG2 等需单独专利评估。

### 3. 已知组件的初步归类

以下只是初步技术判断，合并前仍需逐文件核对：

| 组件 | 许可/来源 | 建议 |
| --- | --- | --- |
| `golang.org/x/image` | BSD-3-Clause | Green；当前已登记 |
| `golang.org/x/text` | BSD-3-Clause | Green；当前已登记 |
| OpenJPEG | BSD-2-Clause | Green 参考/内部化候选；注意文件级声明 |
| lcms2 | MIT | Green 参考/内部化候选 |
| FreeType | FTL 或 GPL 双许可 | 按 FTL 路径使用；逐文件确认 |
| HarfBuzz | Old MIT | Green 参考/可选 |
| Cairo | LGPL-2.1 / MPL-1.1 | Yellow；优先动态链接或独立进程 |
| Poppler | GPL-2.0 / GPL-3.0 | Red；不得链接/复制；只允许 CLI 隔离或行为对照 |
| MuPDF | AGPL | Red；不得进入核心 |
| jbig2dec | 逐版本/逐文件确认 | 未确认前按 Red；不得凭印象复制 |
| PDFium | BSD-3-Clause，但含第三方 | 逐文件确认；只把确认过的文件作为 Green 参考 |

### 4. 内部化宽松许可代码的流程

1. 在 `docs/legal/provenance/<component>.md` 记录：
   - 上游项目、版本、commit、文件清单
   - 原始许可、版权行、NOTICE
   - 修改内容、删除内容、导出接口
   - 对应测试、差分 oracle、fuzz 覆盖
   - 上游安全修复跟踪方式
2. 保留原始版权和许可头；新增文件使用 SPDX 标识。
3. 更新 `THIRD_PARTY.md` 和 `LICENSES/`；生成 SBOM。
4. 只提取必要子集，不把整个上游仓库搬入。
5. 建立上游 commit 跟踪；安全修复必须评估回移。
6. 代码审查同时检查许可头、来源记录和测试是否被污染。

### 5. Clean-room 流程

适用于 GPL/AGPL 或来源不明、但必须自研的组件：

1. Team A 阅读规范、公开文档和黑盒行为，产出需求、格式说明和测试向量。
2. Team B 只接收需求和测试，不接触受限源码，独立实现。
3. 记录 Team A/B 的输入、时间和访问边界。
4. 测试向量如来自受限程序输出，需确认输出本身不受版权保护；否则改用规范构造样本。
5. 代码审查确认没有复制受限实现的结构、注释、命名和常量表。

### 6. Reference-only 规则

- Poppler/MuPDF 等 Red 代码只能用于运行参考程序、比较输出和记录行为，不得复制进
  仓库，包括测试辅助代码。
- 参考实现输出的图像/文本可作为黑盒 oracle，但必须固定版本、参数、字体和 ICC，并
  记录来源。
- 不把参考程序的内部头文件、结构体、常量表或注释翻译成 Go。
- 任何“看起来像直接翻译”的实现都要能回溯到规范条款或独立设计说明。

### 7. CI 与发布门禁

- CI 检查依赖白名单、许可文件、SPDX 头和 `THIRD_PARTY.md` 一致性。
- 新增 module、vendored 代码、生成表、字体/ICC/CMap 数据必须走 ADR 或 provenance
  记录。
- 发布产物包含 SBOM、许可清单和组件来源摘要。
- 没有 provenance 记录的组件不得进入 Core/Preview 默认构建。
- 安全响应流程必须能定位每个组件的上游版本和补丁状态。

## 影响

- 自研/内部化路径变慢，但避免后期许可返工和下游合规风险。
- 允许使用宽松许可代码加速实现，同时保留可替换性。
- GPL 组件仍可通过 CLI 进程用于 Extended，但不得进入 Apache-2.0 核心。
- 每个组件都有明确 owner、版本、许可和测试证据。

## 例外

任何例外必须同时满足：

1. 新 ADR 说明必要性；
2. 法务书面确认；
3. 隔离方式（独立 module/动态链接/进程）明确；
4. CI 和发布清单已更新；
5. 不改变核心的 Apache-2.0 许可承诺。

## 未覆盖

- 具体组件的最终选型
- 专利检索和结论
- 商业支持与上游 SLA
- 生成代码/模型输出的版权归属细则
